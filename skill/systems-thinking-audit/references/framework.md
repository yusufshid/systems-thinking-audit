# Framework Reference

Detailed checklists for each of the four lenses. Read the relevant section as you work through Step 2 of SKILL.md.

## Lens 1: Leverage Points

Based on Donella Meadows' hierarchy — from lowest to highest leverage. When you find a problem, identify which level it actually lives at. A common mistake is fixing a low-leverage symptom (a parameter) when the real issue is a level above it (a goal or a rule).

| Level | What to look for | Example red flag |
|---|---|---|
| 1. Parameters | Temperature, retry counts, thresholds, timeouts | Someone keeps raising a retry limit instead of asking why retries are needed |
| 2. Feedback loop delay/gain | How fast is an error caught, how strongly does the system react | A validation step exists but only runs at the very end of a long chain |
| 3. Information structure | Who/what knows what, what's shared between agents, what's hidden | Two agents make contradictory assumptions because neither sees the other's state |
| 4. Rules | Permissions, what an agent may do autonomously vs. must ask about | An agent can take an irreversible action (delete, send, pay) with no gate |
| 5. Goals | What's *actually* optimized/rewarded/graded, vs. what's written down | A reviewer agent graded on "number of findings" will over-flag |
| 6. Paradigm | The base assumption the whole system operates from — what is this agent *for* | The system prompt frames the agent as "always be helpful" with no room for "should I be doing this at all" |

For each finding, ask: **is the fix being proposed at the same level as the problem, or one level below it?** A goal-level problem needs a goal-level fix, not a parameter tweak.

### Memory / state

This is the Information Structure level (3) in practice — what persists, who can read or write it, and whether it still matches reality. Memory bugs are usually invisible in any single call and only show up as drift over many calls, which is exactly why they're easy to miss in a static read.

1. **Stock vs. flow.** Separate what accumulates across calls/sessions (a memory file, a shared database, running totals) from what's decided fresh each time. A stock is where a small, repeated bias compounds silently — a flow re-derives its answer every time, so it can't drift the same way. When you find a finding elsewhere in the audit (a goal misalignment, a missing check), ask whether its effect is a one-off decision or something that accumulates in a stock — that changes both the urgency and the fix (a bad flow-level decision self-corrects next call; a bad stock keeps being wrong until something explicitly corrects it). Two follow-up questions once you've identified a stock that drives a decision (a reputation score, a blocklist, a trust level, a rolling risk window):
   - **Does it have an outflow, or does it only grow?** A stock with an inflow but no removal/decay/expiry mechanism (entries added to a blocklist but never reviewed for removal, a score that only ever accumulates) trends toward one of two failure modes depending on whether it drives action: if it does, it gets steadily more conservative or restrictive over time as errors never get reversed (a false positive from months ago still silently affects decisions today); if it's just accumulating data, it eventually becomes too costly to query or reason about even if functionally harmless. Ask specifically what removes an entry, not just what adds one.
   - **Does the stock's memory length match the timescale of the risk it's meant to catch?** A rolling window (7 days of loss history, a decay rate on a score) is itself a design decision about how long the past should keep influencing the present. Too short, and a slowly-accumulating risk resets out of the window before it's caught. Too long, and the mechanism keeps reacting to a problem that's already resolved, penalizing current decisions for stale history. This is a specific, nameable way a well-intentioned balancing loop can be ineffective without looking broken — the loop exists, fires correctly, and still doesn't catch or corrects at the wrong pace, purely because the window/decay was tuned to convenience rather than to the actual timescale of what it's supposed to detect.
2. **Write discipline.** Is something written to shared state without anything ever reading it back to validate or use it (dead state that misdescribes the architecture — see the `shared_state.json` pattern: a comment claims coordination that the code doesn't implement)? Conversely, is state read and trusted without checking whether it's still valid, or who last wrote it and why?
3. **Concurrent access.** If more than one process/agent/run can write the same store, what happens on overlap — last-write-wins silently clobbering another run's data, or an actual lock/versioning scheme? This is the same overlap-risk question as scheduled triggers, applied to shared storage instead of shared execution time.
4. **Staleness.** Is cached or stored state ever invalidated, or can a decision be made against information that was true when written but isn't anymore (a cached order status, a customer history snapshot)? A structure with no staleness handling is implicitly asserting "this never changes," which is rarely actually true.
5. **Visibility asymmetry.** In a multi-agent system, does each agent see the same state, or does each hold a private view that can silently diverge from the others'? Two agents acting on different beliefs about the same shared reality is a structural setup for contradictory or duplicated actions, independent of how good either agent's individual reasoning is.
6. **Unbounded growth and recency bias.** Does memory/context ever get pruned or summarized, or does it grow indefinitely? Beyond the obvious cost/context-window concern, unpruned history means an early wrong fact and a later correction can both sit in context with no signal about which one should be trusted — the model has no structural reason to prefer the correction unless something explicitly marks the earlier entry as superseded.
7. **Memory as an unverified self-check.** If a later step trusts what an earlier step wrote to memory as if it were verified fact, that's the same self-check-dressed-as-verification pattern from Lens 2's signal-source ranking, just spread across time instead of across two calls in one turn. A hallucinated or wrong entry, once written, can be treated with full confidence by everything that reads it afterward.

### Permissions / rules

This is the Rules level (4) in practice — evaluating an actual permission/settings config, not just noting whether a gate exists.

1. **Default posture.** Does the system default to denying an action unless explicitly permitted, or default to allowing unless explicitly blocked? Default-allow means every new tool or capability added later is automatically in scope until someone remembers to restrict it — the safe failure mode is backwards, and this tends to get worse over time as a system grows, not better.
2. **Granularity.** Is permission scoped to the specific action/resource/amount the task actually needs (fine-grained), or to a broad category ("can access customer data," "can run shell commands")? Coarse permissions grant more than the task requires, so the blast radius of a mistake is bigger than the task ever called for — this is true even in the case where nothing goes wrong, which is why it's easy to leave unnoticed.
3. **Static vs. contextual.** Is the rule a fixed threshold regardless of situation ("under $100 = auto-approved"), or does it account for context (frequency, recent history, who's asking)? A fixed threshold is really a Lens-1 Parameter; a rule that also considers pattern ("under $100 unless this account already triggered it 3 times this week") is what actually closes the kind of exploit loop described in the cron and memory sections above — a static rule alone can't.
4. **Escalation path.** When a rule blocks an action, what happens next? A defined path (ask a human, queue for review, return a typed error the caller can act on) is a real rules-level design; no defined path just converts "the agent tried something disallowed" into "the task silently failed," which is often just as costly and harder to notice.
5. **Who can change the rules.** Can the agent modify its own permission scope, or write to the config that governs it? An agent that can self-elevate doesn't have rules, it has suggestions. Also check whether the permission check reads anything the agent (or a tool output, or injected content) can influence — a rule enforced against mutable state isn't really enforced.
6. **Enforcement location.** Is the restriction enforced by the model choosing not to act (prompt-level — a preference, bypassable by a sufficiently unusual input or a direct instruction to ignore it) or by something outside the model's control (a code-level gate, an API that rejects the call, a human approval step)? Prompt-only enforcement of something framed as a hard rule is a paradigm wearing a rule's clothing — treat it with the same skepticism as any other prompt-level claim.
7. **Stated vs. enforced.** Does documentation or a comment claim a restriction ("refunds over $500 require approval") that the actual code/config doesn't implement? This is exactly the kind of stated-vs-actual gap Step 6 exists to catch — verify against the config or code itself, not the description of it.
8. **Time-boxed elevation — does it fail open or fail closed?** If a permission can be temporarily elevated (an unlock window, a maintenance mode, a debug flag), check what happens if nobody remembers to revert it: does the elevation auto-expire after a bounded window (fail-closed — the safe default reasserts itself without anyone having to act), or does it stay elevated until someone explicitly reverses it (fail-open — one forgotten step away from a permanent, unintended change of posture)? An auto-expiring window is a meaningfully stronger design than a manual toggle, even when both are technically "temporary."
9. **Does bypassing the gate also bypass the process it exists to protect?** A gate can be code-enforced and still deliver less protection than it appears to, if going around the immediate friction (unlocking, an override flag, an emergency path) also silently skips a deeper process the gate was standing in for — a review checklist, a changelog entry, a required justification. The finding here isn't "there's no gate" (there is one) or "it's prompt-level" (it might be code-enforced) — it's that the gate and the process are two different things, and defeating the first can quietly defeat the second without anyone deciding that should happen. Ask specifically: when someone takes the fast path past this gate, what checks that normally happen *don't* happen as a result?

### Output / distribution

Where a result goes changes its blast radius independent of whether the underlying decision was correct — this section feeds directly into Step 3's risk rating (an action's reversibility is part of what makes a finding Critical rather than Medium).

1. **Reversibility of the channel itself.** A draft saved privately is trivially reversible; a message sent externally isn't (there's no true "unsend," only a correction that some recipients will already have missed); a production deploy affects live users the moment it ships. Rate the channel's own reversibility separately from whether the decision behind it was right — a correct decision sent through an irreversible channel still deserves scrutiny on the channel, because the cost of *being wrong* is what's being assessed, not just the likelihood.
2. **Audience and visibility.** The same output can reach one internal reviewer or thousands of external users. Once something is visible publicly, deleting it afterward doesn't undo who already saw it — so audience size multiplies the cost of the channel-reversibility question above, it doesn't substitute for it.
3. **Automatic vs. staged.** Does output go straight to its destination, or is there a preview/staging/approval step between "the agent decided" and "it's live"? This is a rules-level gate specifically at the publish moment, separate from any gate on the decision itself — a system can have a perfectly good approval process for *deciding* to refund and still auto-send the confirmation email with no review.
4. **Compounding across channels.** One bad decision that triggers several output actions in sequence (money moved, then an email confirms it, then a ticket closes as resolved) gets harder to unwind with each additional channel, because each one leaves an external record instead of an internal, still-correctable state. Count the channels a single decision fans out to, not just the decision itself.
5. **Borrowed authority.** Does the output present itself with the organization's identity (an official-looking email, a public post under a brand account) or is it clearly marked as provisional/automated? Output that carries organizational authority is more costly to get wrong, because the recipient's trust — and whatever they do as a result — is also part of what's at stake, not just the content itself.
6. **Recipient's ability to catch an error.** Some outputs get a free check because the recipient will independently verify them (a code diff a human reviews before merging); others will likely be acted on without any independent check (a "your refund has been processed" notice — the customer experiences the outcome, they can't verify whether it was warranted). Low detectability on the receiving end means the validation has to happen before the output leaves, since nothing downstream is going to catch it either.

### Model / runtime config

This is the Parameters level (1) — the lowest leverage in the hierarchy, which means the discipline here is mostly about *not* over-weighting it. Only raise a finding from this section when it's a plausible secondary contributor to a structural problem found elsewhere; a standalone "consider tuning temperature" note with nothing else behind it is noise, not a finding.

1. **Temperature/sampling as a multiplier, not a root cause.** Nonzero temperature can genuinely add to a problem that's structural at its core — e.g., in a multi-reviewer setup with identical prompt and model, some of the observed "disagreement" is real sampling noise on top of the shared-blind-spot problem, not evidence the reviewers are more independent than they are. Name it as a secondary contributor layered on the structural issue, never as the fix — even temperature 0 wouldn't resolve a same-prompt-same-model independence problem.
2. **Model choice where independence matters.** Using the same model everywhere is a reasonable default for cost/simplicity, and not worth flagging on its own. It becomes a real finding specifically where something is supposed to function as an independent check (a verifier, a reviewer, a synthesizer adjudicating disagreement) — reusing the producer's exact model there weakens the signal per Lens 2's independence ranking. The finding belongs under Feedback Loops (weak signal source); this section is just where to notice it.
3. **Effort/reasoning-depth mismatch.** Does the model's effort or reasoning-depth setting match what's at stake in the decision? A fast/low-effort setting applied to a high-stakes, hard-to-reverse decision (approving a large refund, deciding to deploy) spends the least compute exactly where a mistake is most expensive — a mismatch worth naming even though it's parameter-level, because the direction of the mismatch (cheap compute on expensive consequences) is what makes it worth more than a passing mention.
4. **Context window / truncation behavior.** When a long-running agent's context fills up, what actually gets dropped or summarized — and does anything ensure an early constraint (a permission rule, a scope boundary stated at the start of a session) survives that process? Silent truncation of instructions is a way a rule can stop being enforced without any code change and without triggering the stated-vs-enforced check above, because nothing was ever edited — it just fell out of the window.
5. **Version pinning.** If the model or a key dependency is referenced by a moving alias (e.g., "latest") rather than pinned, behavior can shift under a system that was designed and tested against a specific version's behavior — a leverage point that isn't even under the audited system's own control. Worth a one-line note if the audited material shows this, not worth digging for if it isn't visible.

### Deployment / rollout (changes to the agent itself, not its outputs)

This is distinct from Output/distribution above: that section is about where a *decision* goes once the agent makes it; this is about how a change to the agent's own prompt, code, or config reaches production in the first place. It's a Rules-level question — what gates a new version from full exposure — and it matters precisely because an agent whose individual decisions are all well-gated can still ship a *change* that quietly breaks every decision that follows.

1. **Is there a lower-exposure stage before full production?** A dry-run/shadow mode (the change runs and logs what it would have done, without taking real action) or a staged rollout (the new version handles a fraction of traffic/positions while the rest stay on the known-good version) catches a bad change against real conditions before it can do full damage. Going straight from "changed" to "fully live" makes every update a bet placed with the whole system's exposure at once, regardless of how careful the review process leading up to it was.
2. **Is there an actual rollback path, or just a forward fix?** When a deployed change turns out to be wrong, can the system return to the last-known-good state quickly, or does fixing it require writing and re-deploying another forward change under pressure — which is exactly the condition under which a second mistake is most likely? A rollback path is a fast balancing loop; "just fix it forward" is a slow one that's more likely to compound.
3. **What's actually being validated before promotion?** A staged/shadow period only helps if something is checked at the end of it against a real criterion (did the shadow-mode decisions differ meaningfully from the live version, did the fraction on the new version perform within an expected band) — a staging period that elapses on a timer with nobody looking at the outcome provides the appearance of caution without the substance, the same gap as the config-review-reminder and dormant-loop patterns elsewhere in this file.

### Dependency / supply-chain risk

The agent depends on things outside its own design — a model provider, an RPC/API endpoint, a third-party library — and the health of those dependencies isn't something the system's own good design can guarantee. This is usually a smaller, lower-priority section relative to the others in this file, but worth a quick pass when the audited material shows the actual dependencies in use.

1. **Provider-side change risk.** If the model or a critical API is referenced by a moving target (see Version pinning above) or a provider that can deprecate/change behavior with limited notice, is there anything that would surface that change quickly (a version check, a canary call, monitoring) rather than the system silently operating on assumptions a provider update just invalidated?
2. **Single point of failure on an external dependency.** If a critical path has no fallback when one external dependency is unavailable (one RPC endpoint, one API key, one data source with no backup), the system's uptime is capped by that one dependency's uptime — worth naming explicitly when the dependency also happens to gate something expensive-to-reverse (Output/distribution), since an outage-shaped failure and a wrong-decision-shaped failure can have very different costs even from the same root cause.
3. **If a fallback exists, is switching to it automatic or does it wait for a human to notice?** A redundant second dependency (a backup RPC endpoint, a secondary API key) only closes the loop as fast as its switchover mechanism — automatic failover is a fast balancing loop, "someone has to notice and manually reconfigure" is a slow one with the same gap as any other human-dependent correction (see Human Interface: response-time realism). Not having a second instance is one gap; having one but only failing over manually is a smaller version of the same gap.
4. **Quota/rate-limit exhaustion is a predictable stock depletion, not a random outage — treat it accordingly.** A free-tier or metered dependency (API credits, RPC rate limits) has a usage stock that depletes with an outflow the system itself controls (its own call volume), unlike a provider outage, which is an external event. This means it's foreseeable in a way an outage isn't — check whether remaining quota is visible anywhere with a warning threshold before hard depletion, or whether the system only discovers the limit reactively when a call starts failing. The stock-outflow question from Memory/state applies here directly: is there any visibility into this particular stock before it hits zero?
5. **Does an automatic recovery event still get surfaced to a human?** If the system self-heals from a dependency failure (auto-switches to a fallback, retries successfully), silence about that recovery removes the one signal that would otherwise indicate a growing problem — a primary dependency that fails over automatically once a month is invisible under this design, and fails over automatically once a day is *equally* invisible, even though the second case is a leading indicator worth acting on before the fallback itself becomes unavailable too. A degraded-but-self-healing state and a fully-healthy state should not look identical to whoever's responsible for the system.
6. **A monitor can consume the same resource it's protecting.** A health-check that polls a rate-limited or metered dependency to detect exhaustion is itself a consumer of that dependency's quota — if it's tuned for maximum vigilance (poll as often as possible) without regard for its own footprint, it can measurably worsen the exact problem it exists to catch. Check whether a monitoring mechanism's own frequency was deliberately budgeted against the limit it's watching, or just set to "as often as seemed reasonable" independent of that constraint.
7. **Failure mode on exhaustion is not uniform across dependencies — verify each one, don't assume.** Two metered dependencies that look similar (both API-key-gated, both usage-based) can fail completely differently when a limit is hit: one might auto-charge a payment method to keep functioning (a financial-risk failure mode), another might silently reject or rate-limit requests (an availability-risk failure mode). These call for different mitigations and different urgency, so treat "what happens when this dependency's quota runs out" as a per-dependency question to actually verify against the provider's real behavior, not an assumption carried over from a different dependency that happened to behave one way.

## Lens 2: Feedback Loops

For every check/validation/review mechanism you can find in the system, answer:

1. **Reinforcing or balancing?** Does this loop correct deviation (balancing) or amplify it (reinforcing)? Reinforcing loops are fine if intentional (exploration, confidence-building); dangerous if accidental (errors compounding through unchecked memory/context).
2. **What's the signal source?** Rank from weakest to strongest independence:
   - Self-check (same agent, same prompt, same context re-reads its own work) — weakest, shares blind spots with the thing it's checking
   - Verifier/reviewer using the *same* model/prompt as the producer — looks independent, often isn't
   - Verifier/reviewer that's genuinely independent (different prompt, different framing, or a different model)
   - Environment ground truth (test results, command exit codes, API responses) — strongest, can't be talked into agreeing
   - Human-in-the-loop — strong but slow/expensive
3. **What's the delay?** How many steps/how much time between an error occurring and it being caught? Long delays let reinforcing dynamics run further before correction.
4. **What's the gain?** Does the correction over-react to small signals (causing oscillation — the agent flip-flopping) or under-react (correction too weak to matter)?
5. **Is there a balancing loop at all** on every action that's expensive to reverse (sending a message, deleting data, spending money, publishing)? If not, that's usually a Critical or High finding regardless of how good everything else looks.
6. **Is a loop that appears to exist actually active?** A balancing loop can be fully designed and even implemented in code, yet never actually fire — a notification channel with an empty recipient ID, a check gated behind a flag that defaults off, a cron job registered but never actually scheduled on the host. This is a distinct failure from "no balancing loop was built": here, the design is correct and someone can point to the code that implements it, which makes it easy to assume it's working. Verify activation, not just presence — ask "when was this last observed to actually fire," not just "does this exist in the codebase." A loop that exists on paper but isn't wired up provides zero actual correction, identical to it not existing, but is far more dangerous because it creates false confidence that a check is happening.
7. **Self-reinforcing scoring or weighting mechanisms.** A mechanism that increases a signal's influence because it performed well recently (a confidence score that boosts on success and decays on failure, a ranking that favors whatever's been chosen before) is a reinforcing loop by construction — and unlike most reinforcing loops that emerge by accident, these are usually built on purpose, which makes them easy to under-scrutinize. The risk is specific: without a floor, ceiling, or decay strong enough to counteract a lucky streak, the mechanism can't distinguish "this is genuinely good" from "this got lucky a few times in a row" — it amplifies whatever happened recently, noise included. This is a Critical-adjacent finding whenever the amplified signal drives a consequential decision (capital allocation, autonomous action priority, trust ranking) — check specifically for clamping/decay parameters and ask whether they were tuned against a case where the mechanism should have *stopped* trusting a signal that had been rewarded.

### Automated / scheduled triggers (cron, `/loop`, recurring tasks)

If the agent runs on a schedule rather than only in response to a human, the trigger mechanism itself is part of the feedback loop and needs its own check — frequency and impact together determine how dangerous a bad loop can get before anyone notices:

1. **Frequency sets the delay.** A cron interval isn't just an implementation detail — it's the correction delay for any reinforcing loop the agent might get stuck in. Every run between "something went wrong" and "a human is likely to look" is a run where the problem could compound unnoticed. A tight interval on a low-stakes check is fine; a tight interval on something that can take irreversible action is a Critical-risk combination regardless of how good the agent's own logic is.
2. **Impact-per-run sets the gain.** Does each scheduled run only read/report, or does it act (send messages, modify data, deploy, spend money)? High frequency + high impact-per-run is the worst combination: a runaway loop gets many chances to do damage before a human's response time (which doesn't scale down with the cron interval) can catch up.
3. **Overlap risk.** If a run can take longer than the interval between runs, check whether runs can overlap. Overlapping runs on shared state is a classic accidental reinforcing loop: each overlap slows the system further, increasing the odds of the next overlap too — and it's rarely intentional, just a mismatch between an interval chosen for convenience and actual task duration under load.
4. **Retry/failure behavior.** Does a failed run retry immediately next cycle with no backoff? If the failure cause is persistent (a downstream API down, a bad state), a naive fixed-interval retry just re-applies the same failing action over and over, which can itself be the reinforcing loop (repeated load on an already-struggling dependency, repeated partial writes, repeated alerts).
5. **Notification fatigue as a dying balancing loop.** If a human is the balancing mechanism (they get paged/notified and intervene), check what happens under sustained failure: a schedule that pages on every failed run, with no escalation or de-duplication, trains the human to mute or ignore it — the balancing loop doesn't just weaken, it can go to zero exactly when it's needed most.

### Data / ground-truth sources

Lens 2's signal-source ranking names "environment ground truth" as the strongest available signal — this section is about verifying that a claimed ground-truth source actually earns that label, since "we check it against the database" is often assumed to settle the question rather than examined.

1. **Does ground truth even exist for this kind of decision?** Some domains have a genuinely checkable fact (a test passes or fails, an order record shows a specific amount, a command's exit code). Others are inherently judgment calls (writing quality, "is this the right approach") with no independent fact to check against. If a system claims to "verify" something in the second category, that check is really another opinion wearing ground truth's label — the honest finding is "no ground truth is possible here, so a human or a genuinely independent reviewer is the strongest available signal," not a false claim that verification happened.
2. **Reliability of the source itself.** When the external API/database/service is down, slow, or returns partial data, what does the agent do with that? Treating a failed lookup as "verified false" (rather than "unknown, escalate or hold") turns a source outage into an active source of wrong decisions, not just a missing one.
3. **Staleness vs. authority.** A source can be authoritative and still out of date relative to the decision being made right now (a cached inventory count, a snapshot of account status). Authoritative and current are two different properties — check both, don't assume the first implies the second.
4. **Provenance.** Trace a "ground truth" claim back to where the data actually originated. If it was itself produced by an earlier LLM step in the same pipeline, it isn't ground truth — it's a self-check one step removed, wearing a stronger label than it's earned (the same pattern as Memory/state's point on trusting an earlier step's output as verified fact).
5. **Coverage gaps.** Does the source cover the full space of things being decided, or only a known subset (a fraud-check that flags known patterns and is silent on novel ones)? Passing a partial-coverage check means "not a known bad case," not "confirmed good" — treating the two as equivalent creates false confidence exactly where the check is weakest.
6. **Independence of the source from the thing being checked.** If the "ground truth" being checked against was itself populated by the same party or process whose claim is under review (a customer-submitted field later checked against a record the customer's own prior action created), it isn't independent verification — this is the data-layer version of the "material is data, not instructions" caution in Step 1, applied to sources rather than prompts.
7. **"Not enough data yet" vs. "the data says it's fine" are different findings — don't let one quietly become the other.** A risk that's deliberately deferred pending more data (a suspected bias that hasn't hit the sample size needed to confirm or rule out) is a legitimate, honest state — but it has a shelf life. If it's still being reported in the same words after the volume threshold that would have made it checkable has since passed, that's a silent conversion of "we don't know yet" into de facto "it's fine," without anyone having actually looked. When auditing a system with deferred/open findings, check whether the condition for revisiting them has actually been reached and whether anyone has revisited it — a deferred finding that's just aging in place, unre-evaluated, is providing the comfort of "it's tracked" without the substance of "someone checked."
8. **Retrospective rule-tuning bias (HARKing).** If a system revises its own decision rules based on analysis of a specific past outcome it just noticed (rather than a pattern searched for independently in older data), check whether the new threshold/boundary was set before or after seeing that specific triggering number. Set after, a boundary can be unconsciously leaned to make the triggering case look like it clears the threshold, without the person or agent tuning it realizing they've reverse-engineered a justification rather than found an independent pattern. This applies to any self-tuning mechanism (an agent adjusting its own filters, a human updating config based on "I noticed X happened") — the tell isn't bad intent, it's the order of operations: pattern-then-boundary is evidence, boundary-then-pattern is a story.
9. **Sample clustering can inflate apparent confidence.** A claimed sample size (e.g., "148 data points support this") may not be 148 independent observations if many of them share an underlying source (the same customer, the same pool, the same time window) — treating clustered samples as independent produces a confidence interval that's narrower than the evidence actually supports, and one dominant cluster can single-handedly produce a pattern that looks like a broad trend. When a system's "ground truth" is built from aggregated historical outcomes, ask what the samples actually cluster by and whether the stated confidence accounts for it — and separately, whether a robustness check was run (does the conclusion survive removing the single largest/most extreme cluster or outlier, or does it flip). A related discipline for systems that test many hypotheses/rule candidates at once and act on whichever "pass": more simultaneous hypotheses means a higher chance one passes by chance alone, so check whether the system requires independent replication before acting on a single passing result, or treats every hypothesis test as if it were the only one run.

### Human interface

Lens 2's signal-source ranking calls human-in-the-loop "strong but slow/expensive" — this section checks whether a human checkpoint actually delivers that strength in practice, since a human notified badly provides almost none of it.

1. **Actionability of the ask.** When the agent escalates or requests approval, does the human get the specific claim, the evidence behind it, and the stakes — or just a vague ping ("something needs review")? A notification without enough context to decide just moves the burden of investigation onto the human without actually transferring the decision; the loop is nominally balancing but functions closer to reinforcing, since an under-informed human will often just approve.
2. **Response-time realism.** Does the system assume a human responds within a timeframe that matches how people actually work (not always watching, may be offline or asleep)? Check what happens on timeout: proceeding without approval defeats the point of asking, but blocking indefinitely with no fallback creates its own failure mode. Which one happens, and is it the right default for what's at stake?
3. **Approval-UI affordances.** Is approving as easy as one click with the actual decision buried or not shown (making rubber-stamping the path of least resistance), or does approving require actually seeing what's being approved? This is the Tools/Affordances checklist applied to the human side of the interface — a one-click "approve" with no visible context trains the same click-through-without-reading behavior the agent's own tool design can create.
4. **Volume and batching.** If a human is expected to review many items, does the volume make careful review impractical? This is the notification-fatigue pattern from the Scheduling/triggers section, but for approval queues rather than alerts — someone facing 200 pending approvals a day will approve faster and less carefully than someone facing 3, and the interface rarely accounts for that shift.
5. **Feedback to the human about outcomes.** Does whoever approved or reviewed something ever learn what happened afterward — was the judgment right, did it cause a problem downstream? Without this, a human-in-the-loop can't calibrate over time, which is itself a missing balancing loop — just at the level of human performance rather than agent performance.
6. **Right human, not just a human.** Escalating to someone without the context or authority to actually decide is functionally equivalent to no escalation at all — check that whoever gets notified is positioned to act, not just available to receive a message.

### Cost / economics as a feedback signal

Every call an agent makes has a cost (tokens, API fees, compute, gas), and that cost is itself information the system can either use or ignore. This is easy to miss because it's not usually framed as a "feedback loop" question, but it is one: does spending more ever feed back into a decision, or does the system spend the same way regardless of what it's getting for it?

1. **Is cost visible to anything that could act on it?** If nothing in the system ever sees its own operating cost (per-decision, per-session, or aggregate), cost can't function as a constraint even in principle — it's not that the constraint is weak, it's that the signal doesn't exist yet for a constraint to attach to. Contrast with a system that logs cost per outcome and can therefore ask the next question.
2. **Does cost ever gate or throttle a decision, or is it purely observational?** A cost dashboard that nobody's decisions depend on is a read-only report, not a feedback loop — compare to the notification-fatigue and dormant-loop patterns elsewhere in this file: a signal that exists but drives no action provides the appearance of oversight without the substance.
3. **Can the system become economically unsustainable without any single decision being wrong?** This is the systemic version of the concern: every individual call can be reasonable in isolation (a retry here, a verification pass there) while the aggregate cost quietly exceeds whatever value the system produces — the same "many individually-reasonable decisions compound into an outcome nobody chose" pattern as Lens 3's multi-step accumulation, just measured in cost rather than behavior. This is worth checking explicitly on any system with retry loops, multi-agent fan-out, or per-call verification (all of which multiply cost per unit of output) — see the retry-loop and multi-researcher examples elsewhere in this file, which are cost multipliers as much as they are quality/goal issues.
4. **Coverage symmetry across loss categories.** If the system has a circuit breaker or balancing loop for one category of loss (a portfolio-level trading drawdown limit, a spend cap on one channel), check whether a mechanically similar category of loss has an equivalent protection — or whether coverage is asymmetric because one category got attention and a parallel one didn't. Concretely: a runaway loop or bug can just as easily cause excessive API/LLM spend as it can cause bad trading decisions, but a system can have a mature circuit breaker for the latter and none at all for the former, especially when an auto-recharge/auto-top-up feature on a billing account means the cost side can compound without anyone approving each increment. Don't assume protection for one loss type implies protection for others that share the same triggering mechanism.

### Incident response / postmortem loop

This is a slower, higher-level loop than the per-decision feedback loops elsewhere in this lens — it's the loop that's supposed to activate *after* something has already gone wrong, and its job is to make sure a failure changes the system, not just gets patched and forgotten.

1. **Does a structural fix follow, or just a symptom-level patch?** After an incident, check whether what actually changed addresses the root cause (a goal redefinition, a new balancing loop, a rules-level gate) or only the immediate symptom (a one-off manual correction, a config tweak that doesn't generalize). A pattern of symptom-level patches after repeated similar incidents is a live instance of Shifting the Burden (see System Archetypes) — treat it as such rather than as a series of unrelated one-off fixes.
2. **Does the fix get reflected back into the system's own reference material?** If an incident reveals a gap, and the fix lives only in someone's memory or a chat thread rather than in the documentation, config, or skill that governs the relevant behavior, the same failure mode is available to recur — this is the incident-response-specific case of the documentation-completeness check (Lens 4, Paradigm).
3. **Is there a loop at all, or does "the incident is over" substitute for "the incident was resolved"?** A system with no postmortem practice can look stable simply because nobody is comparing incidents to each other — check whether anything would surface if the same category of failure happened three times in three months, or whether each occurrence is handled in isolation with no memory connecting them (a Memory/state gap applied specifically to the record of past failures).

## Lens 3: Emergent Behavior

This lens requires imagining the system *running*, not just reading its parts. Ask:

1. **Multi-step accumulation** — could a sequence of individually-reasonable decisions compound into a strategy nobody designed? (E.g., an agent that "discovers" a shortcut through many small locally-optimal choices.)
2. **Multi-agent interaction** — if there's more than one agent, could they end up waiting on each other, duplicating work, or reinforcing a shared bias because they come from the same base prompt/model?
3. **Combinatorial surface** — how many tools/agents/paths are in play? More surface means more untested combinations; ask whether anyone has actually exercised the unusual combinations, not just the common path.
4. **Proxy metric drift** — is the agent optimized/evaluated against a stand-in for the real goal (task count, response length, "helpfulness" score)? Could it satisfy the proxy while missing the actual intent? This is a goal-level problem (Lens 1) that manifests as emergent behavior.
5. **Latent capability activation** — does giving the base model new tools/autonomy risk surfacing capabilities/behaviors that were never explicitly designed for, just because the model is now capable of chaining them?

Findings here are usually *plausible scenarios*, not observed bugs — say so explicitly, and rate risk by how likely and how costly the scenario is, not by whether you've seen it happen.

### Orchestrator / leader agents (an agent whose job is managing other agents)

When the system under audit is itself a leader coordinating subagents — delegating tasks, collecting results, deciding what runs when — most of its risks are the multi-agent-interaction point above, sharpened by the fact that this agent's entire job *is* the coordination. A leader that just does Multi-agent interaction and Combinatorial surface checks above is a good start; also check:

1. **Delegate or verify — pick one, and know which.** Is the leader's role to *collect* subagent outputs, or to *adjudicate* them? These sound similar but aren't: a collector just needs good routing; an adjudicator needs an actual reconciliation mechanism (Lens 2). A leader built as a collector but expected (implicitly, by whoever reads its output) to behave like an adjudicator is the exact gap behind contradictory multi-reviewer reports — the fix is deciding which role it's meant to play and building the mechanism that role requires, not assuming "coordinating" already implies "verifying."
2. **Visibility into subagent reasoning, not just subagent output.** Does the leader see *how* a subagent reached its answer (which would let it notice a shaky basis for a claim) or only the final answer (which it can only take at face value)? "Fire and forget" delegation with no visibility into process means the leader's own oversight is structurally shallow, regardless of how carefully it reads the outputs it does get.
3. **Paradigm consistency across the team.** Does the leader assume all subagents share its goals and priorities, when in fact some were built or prompted for a narrower, different purpose? A leader that doesn't know its subagents implicitly disagree about what matters will misread a real conflict of purpose as noise or inconsistency to average out, rather than a signal to investigate (see Lens 4, point 5).
4. **Task starvation and load distribution.** Does delegation logic distribute work evenly relative to subagent capability, or can some subagents end up starved of meaningful work (idle, or only ever handed the edge cases nobody else wants) while others are overloaded? This is an information-structure/goal question, not a performance detail — it changes what the system as a whole is actually capable of noticing or doing well.
5. **Leader as bottleneck.** If every decision must route back through the leader before subagents can proceed, check whether the leader's own latency (or its own turn to think) becomes the system's limiting factor as the number of subagents grows — a structure that looks parallel on paper can still be serial in practice if everything funnels through one coordination point.
6. **Stale model of the team.** Does the leader's understanding of what each subagent can do stay accurate, or can it act on an outdated picture (assigning a task to a subagent whose capability, prompt, or tools changed since the leader last "learned" about it)? This is the Memory/state staleness check, applied to the leader's model of its own team rather than to external data.
7. **Accountability gap.** When a subagent's output is wrong, does responsibility trace back cleanly to a specific check that should have caught it, or does the hierarchy diffuse it — everyone assumed someone else in the chain verified it? A structure where no single component owns "did we get this right" is the leader-agent version of the missing-balancing-loop finding, just spread across a hierarchy instead of sitting in one obvious gap.
8. **The leader's own oversight can be a self-check in disguise.** If the leader evaluates or ranks subagent outputs using the same model/prompt family as the subagents themselves, its "oversight" shares whatever blind spot produced the subagents' outputs in the first place — apply Lens 2's signal-source ranking to the leader's own judgment, not just to whatever the subagents produce.

## Lens 4: Paradigm / Mental Model

Ask where the agent's sense of "what am I for" actually comes from, and whether it's consistent:

1. **Explicit system prompt / instructions** — what does it say the agent's role and priorities are? Does it ever contradict itself, or leave the actual priority ordering implicit?
2. **Organizational conventions** (CLAUDE.md, style guides, shared config) — do these align with the system prompt, or quietly pull in a different direction? Check completeness as well as alignment: for the failure modes and operational decisions this agent (or the humans running it) will actually face, is there written guidance anywhere — or does critical knowledge exist only in one person's head, scattered across code comments with no central reference, or nowhere at all? This is different from an unstated assumption (point 6 below, which is about something nobody realized needed checking) — this is about a gap people already half-know exists ("we should really document what to do if X happens") that never got written down. A system with rich, current docs covering its safety mechanisms (an architecture doc explaining a circuit breaker, a runbook for a known failure) passes this check regardless of how the rest of the audit goes; a system where that knowledge is undocumented is one bus-factor incident away from operating blind.
3. **Tool design and affordances** — do the available tools imply a worldview? (E.g., an agent whose only destructive tool is `delete` will lean toward deleting when uncertain, simply because that's what's on offer.) See the dedicated checklist below.
4. **Base model training** — for anything that can't be changed by prompting, note it as a known constraint rather than a fixable finding — the audit should distinguish "you can fix this by editing a file" from "this is baked into the model and needs a different mitigation (e.g., a guardrail, not a better prompt)."
5. **Consistency across multi-agent systems** — if there's more than one agent, do they share a paradigm, or does each subagent implicitly believe something different about the system's purpose? Divergent paradigms between agents is a common, underrated source of the kind of emergent behavior in Lens 3.
6. **Unstated assumptions.** The explicit paradigm is what the prompt says the agent is for; underneath that is whatever the system assumes is true and never states or checks anywhere — "the customer is telling the truth," "the data source is current," "there's only ever one instance of this running." Ask directly: what does this system act as if it can take for granted, that nobody wrote down and nothing verifies? An unstated assumption is more dangerous than a stated one precisely because there's no line to edit when it turns out to be wrong — find it by asking what would break silently, not loudly, if the assumption failed.

### Tools / affordances

A tool list isn't a neutral menu — what's on it, and how each option is described, quietly tells the agent what kind of situation it's in and what a reasonable response looks like. Read the actual tool schemas and descriptions (not just the prompt's summary of them) and check:

1. **Affordance asymmetry.** Does the tool set skew toward one kind of action — mostly destructive/mutating (delete, send, execute) with no low-stakes alternative, or mostly passive (read-only) with one high-stakes escape hatch? An agent with no cheap, reversible option will use the expensive one more often than the situation actually calls for, simply because it's what's available. Check specifically for the presence (or absence) of a low-stakes fallback — an escalate/flag/ask-a-human tool — for situations that don't clearly warrant the bigger action.
2. **Description-vs-effect mismatch.** Does a tool's name or description undersell what it actually does? (`update_record` that actually overwrites and can't be partially applied; `archive` that's actually a hard delete.) The agent forms its sense of risk from the tool's description, not from reading the implementation — a mismatch here means the agent's caution calibration is wrong by design, independent of how careful the prompt tells it to be.
3. **Irreversibility signaling.** Does anything in the tool's schema or description flag that an action can't be undone (vs. every tool reading as equally casual)? If irreversibility is only communicated in prose elsewhere in the prompt, it's one edit away from being dropped or missed — the tool boundary is a more durable place to encode that than a sentence the model has to remember to apply.
4. **Granularity mismatch.** A single coarse tool that bundles several decisions into one call (e.g., one `resolve_ticket(action, refund_amount, close)` doing everything at once) removes the natural checkpoints that several smaller tool calls would create — there's no seam left where a check could be inserted between "decide" and "execute all of it." Conversely, tools that are too fine-grained can force so many calls that a real check becomes tedious enough to skip.
5. **Overlapping/redundant tools.** Multiple tools that accomplish similar ends (two ways to send a message, two ways to modify the same resource) create an implicit choice the agent makes on its own, often based on which is more prominent or easier to call correctly — not necessarily which is safer. This also expands the combinatorial surface from Lens 3 without adding real capability.
6. **Unsafe defaults.** Optional parameters that default to the more permissive or more destructive behavior (e.g., a delete tool that defaults to non-recoverable unless a `soft` flag is explicitly passed) put the burden of safety on every call site remembering to opt out, rather than opting in.

This checklist and the Rules level in Lens 1 overlap by design — a missing approval gate is a Rules-level finding about *permission*, while a tool's affordance is about what the *option itself* silently implies before permission even enters the picture. A tool can be perfectly gated and still shape behavior badly through how it's described.

### Skill portfolio (for agents built from modular skills/instructions)

For an agent whose behavior is composed from a set of conditionally-loaded skills (rather than one monolithic prompt), the skill portfolio itself needs the same governance scrutiny as any other component — a skill actively shapes behavior when it triggers, so an unmaintained one isn't inert documentation, it's live instruction that may no longer match reality.

1. **Coverage.** Do the skills actually span the tasks this agent regularly handles, or are there frequent, recognizable task types with no matching skill — meaning the agent improvises the same kind of decision from scratch each time, with no accumulated, reviewed process behind it? A gap here is the skill-portfolio version of the documentation-completeness check above: something people already know matters but never got turned into a reusable, reviewed skill.
2. **Role clarity and overlap.** Does each skill have a clearly scoped trigger and purpose, or do two or more skills compete for the same kind of request? Overlapping skills create the same ambiguous-choice problem as overlapping tools (see Tools/affordances above) — which one fires can depend on wording rather than intent, and nobody designed for that outcome.
3. **Staleness.** A skill encodes assumptions about the system it operates on — config keys, architecture, available tools. When the underlying system changes, does anything ensure the skill is revisited, or can it keep confidently instructing behavior based on a version of the system that no longer exists? This is a sharper case of the stated-vs-enforced problem (Lens 1, Rules) precisely because a skill isn't passive documentation a human might skim skeptically — it's instructions an agent will execute with full confidence unless something catches the drift.
4. **Review/upgrade cadence — is there a governance loop for the skill portfolio itself?** Ask directly: what mechanism, if any, periodically checks whether skills are still accurate, still triggering on the right inputs, and still non-overlapping — and is that mechanism itself active (see the dormant-loop check in Lens 2) or just theoretically present? A skill set that's written once and never revisited is a live instance of Shifting the Burden (Meadows archetype, below): each skill was a good fix for a real gap at the time, but without a recurring review, the portfolio only ever grows and never gets re-validated against how the system has actually evolved.
5. **Orphaned skills.** Does every skill in the portfolio still actually get invoked, or has something else silently superseded a skill's purpose while it remains present — adding maintenance and cognitive overhead (another thing a reader has to understand when reasoning about the system) without providing current value? Treat an orphaned skill as a smaller-scale version of the dead-code finding in Memory/state (Lens 1): present, described, but not doing anything.

## System Archetypes (Meadows)

Beyond the leverage-point hierarchy, Donella Meadows and the wider systems-thinking tradition name recurring failure *patterns* — shapes a system's behavior falls into regardless of the specific domain. Recognizing one of these by name is often faster than re-deriving the mechanism from scratch, and it signals to the reader that the problem is a known category with known intervention points, not a one-off quirk of this particular agent. Per Step 2, actively check the findings you already have against this list before moving on — you're not hunting for a new finding, you're checking whether findings from different lenses are actually the same archetype, which is exactly the connection Step 5's System Map should name. Only name one if it genuinely fits, don't force a match, and when one does fit, say so explicitly in the System Map ("this is a Shifting the Burden pattern: ...") rather than only describing the mechanism without naming it.

1. **Shifting the Burden.** A quick, local fix gets used repeatedly in place of a fix to the actual root cause, and the system becomes dependent on the quick fix — so dependent that the underlying capability it was supposed to be a stopgap for never gets built, or quietly atrophies. In agent systems: a retry loop papering over a goal-definition problem (see the `run_with_retry` codebase example throughout this file), or routing everything uncertain to human escalation instead of ever building a better internal check — the human queue becomes the system's real quality mechanism by default, and nobody notices the agent's own judgment never improved because the burden was always shifted elsewhere.
2. **Success to the Successful.** Whichever part of a system is already doing well keeps getting more resources/attention, and whichever part is struggling gets starved of the resources it would need to catch up — the gap widens on its own, without anyone deciding it should. In agent systems: see the Orchestrator/Leader Agent section above (task starvation) — a leader that routes easy or high-visibility work to its best-performing subagent "because it's reliable" guarantees the other subagents never get the practice or data needed to improve.
3. **Escalation.** Two sides each respond to the other's last move by raising the stakes further, with no ceiling built into the system to stop it — each round looks locally rational (matching or slightly exceeding the other side) even though neither side chose the eventual extreme outcome. In agent systems: a fraud-detection agent and adapting bad actors, two negotiating/bidding agents with no cap, or a moderation agent and users iteratively finding the edge of its rules — each side's "reasonable" response to the other is what drives the drift, not a bug in either one individually.
4. **Policy Resistance.** Multiple actors each pull the system toward their own sub-goal, so that any single intervention gets absorbed or countered by the others' pull rather than actually changing the system's behavior. In agent systems: this is the deeper reason a single patch to one subagent in a multi-agent system often doesn't stick — if the subagents (or the humans configuring different parts of the system) have quietly divergent paradigms (Lens 4, point 5), a fix aligned with only one of those paradigms will be worked around by the parts still pulling the other way.
5. **Rule Beating.** An agent (or the system it's embedded in) satisfies the literal rule while defeating its purpose — this is the formal name for what this framework elsewhere calls proxy-metric drift or Goodhart's Law (Lens 1, Goals; Lens 3, point 4). Naming it as Rule Beating is useful specifically when the "rule" in question is a hard constraint or permission check rather than a soft goal metric — e.g., an agent that stays technically within a spending limit by splitting one large action into several smaller ones, satisfying the letter of a per-transaction cap while defeating the reason the cap existed.

**Hierarchy, as a system property rather than a trap (multi-agent systems only).** Meadows describes hierarchy itself as something a healthy system needs in the right balance: subsystems need enough autonomy to respond to their own local conditions, and the larger system needs enough coherence that the subsystems' local choices don't add up to something nobody wanted. This is auditable, not just theoretical — check for concrete evidence of either failure direction:

- **Over-control**: does every subagent decision have to route back through a leader/orchestrator before proceeding? Does a subagent with clearly better local information about a specific case still have to wait for top-down sign-off on routine matters? This is the bottleneck direction — coherence bought at the cost of responsiveness.
- **Under-coordination**: can subagents act on their own conclusions with nothing above them reconciling contradictions, duplicated work, or conflicting actions on shared state? This is the fragmentation direction — autonomy bought at the cost of coherence (the multi-reviewer contradiction case throughout this file is the canonical example).

State explicitly which direction, if either, the evidence points to — "reasonably balanced" is a fine conclusion if that's genuinely what you find, but it should follow from checking both directions, not from not having looked. Both directions are the same underlying balance struck in the wrong place, not two unrelated problems — and this is also where the Orchestrator/Leader Agent section's bottleneck-vs-starvation tension comes from.
